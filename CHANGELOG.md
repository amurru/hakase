# Changelog

All notable changes to hakase are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
During the alpha phase (0.x), breaking changes may land in any minor release;
the web UI and `config.json` formats aim for backward compatibility but are not
guaranteed stable until 1.0.

## [Unreleased]

### Added

- **Session checkpoints / restore-to-message rewind** - every conversation now has rewind points: a snapshot of the full session file is taken just before each user message is recorded (web chat, TUI send paths, and Telegram all flow through the one persistence choke point), stored under `sessions/.snapshots/<session id>/` (0600, atomic writes under the store's flock, invisible to the session index) with a per-session retention ring (`session.snapshots.max`, default 50; `session.snapshots.enabled: false` stops taking them). "Restore to before this message" on any persisted user prompt in the chat UI opens a snapshot dialog (timestamp, message count, preview, preselected to the prompt's own rewind point) and restores in three clicks: the current state is first captured as a `pre-restore` undo snapshot — so restore is itself undoable — then the session file is replaced with the snapshot's content through the store's atomic path, keeping the same session id so project binding and registered-project sandbox pinning survive (acceptance criterion 3). Restore refuses with 409 while the agent is working (same guard as compact), snapshots die with their session (delete + stale cleanup), and everything is truncation-with-a-net rather than branch-fork — see [docs/session-rewind/](docs/session-rewind/spec.md).
- **OpenTelemetry GenAI tracing** - one waterfall trace per agent run, exported over OTLP/HTTP to any GenAI-aware collector (Jaeger, Grafana Tempo, Langfuse, Datadog): a `hakase.run` correlation root per transport run (session id, task id, bound project, transport, provider outcome mapped from the canvas status vocabulary) nests ADK's built-in GenAI spans — `invoke_agent` per agent activation, `generate_content` per LLM call with `gen_ai.usage` token counts (input, output incl. reasoning, cache reads) and finish reason, `execute_tool` per tool call — plus `retrieval knowledge` spans on `recall_knowledge`/`search_knowledge` with result counts. Web, Telegram, TUI, and cron runs all share one trace shape (the driver gained `agentrun.NewForTransport`; delegated sub-agent spans parent via ctx propagation with no delegation-code changes), MCP tool calls propagate W3C `traceparent` through `_meta` per SEP-414 via a go-sdk sending middleware, and the audit log's session id now joins to a trace via `hakase.session.id`. Off by default and honest about it: `tracing.enabled: false` installs nothing (no provider, no exporter goroutine, no network traffic), enabled tracing validates its endpoint at startup (fail-loud — the exporter itself only logs parse errors), a pathless endpoint targets the collector at `/v1/traces` while path-shaped vendor endpoints pass through verbatim, and `headers`/`sample_ratio` (default 1) cover vendor auth and head-based sampling. Env overrides: `HAKASE_TRACING_ENABLED` / `_ENDPOINT` / `_SAMPLE_RATIO` / `_HEADERS`. GenAI semconv are still Development status, so every hakase-owned attribute key is pinned as a literal in `internal/tracing` rather than tied to a semconv package version - see [docs/otel-tracing/](docs/otel-tracing/spec.md).
- **Agent-written auto-memory** - the orchestrator can now carry facts across sessions through its own notes: `remember` saves a short typed note (`user` / `feedback` / `project` / `lesson` — update by passing an existing id), `forget_memory` deletes one, and every new session starts with an `AUTO MEMORY` block (note ids included) injected once per session ahead of history, scoped to the session's project root plus global notes and capped by `memory.max_prompt_chars` (default 4000, truncation disclosed in-block). Notes persist at `~/.hakase/memory/notes.json` (0600, flock held across the read-modify-write transaction, atomic tmp+rename with mode tightening, corrupt-file quarantine, mirrors the channels-state store), are deduped on exact match, and the store refuses writes past `memory.max_notes` (default 200) with an actionable error instead of evicting silently. `memory.enabled: false` (or `HAKASE_MEMORY_ENABLED`) removes both the tools and the injection entirely; tools are orchestrator-only (sub-agents never see them). Surfacing for human pruning: a web UI Memory panel (list, filter, delete under the existing auth middleware) and `hakase memory list|add|forget`, which work while the server runs. The optional session-end extraction pass and a TUI command are deferred - see [docs/auto-memory/](docs/auto-memory/spec.md).
- **MCP 2026-07-28 upgrade (go-sdk v1.7 + ADK v2.4)** - the MCP client now speaks the stateless protocol revision: dependency bump (go-sdk v1.4.1 → v1.7.0, ADK v2.1.0 → v2.4.0, MVS-cascaded genai/openai-go/OTel) with old-revision servers still working via the SDK's negotiation fallback (covered by a stateful+stateless smoke matrix test). **Elicitation rides the existing gates**: every managed server gets its own MCP client with an elicitation handler that routes server input requests into hakase's approval/clarify machinery - a remote server's boolean confirm lands as an approval card (web UI + Telegram inline keyboards + TUI, first responder wins, session-routed), form fields as clarify prompts (JSON-schema enums become choice buttons, other primitives free text with type coercion), URL-mode elicitations surface the link as a non-blocking clarify prompt, multi-property schemas decline closed, and headless runs (cron) fail closed. Timeout maps to decline, user cancel to cancel. **OAuth for remote servers (CIMD)**: the reserved phase-3 `oauth` config stub became a real schema - `client_id_url` (Client ID Metadata Document, https + non-root path enforced) or pre-registered `client_id`/`client_secret`, optional `redirect_url`/`scopes` - wired through the go-sdk's `AuthorizationCodeHandler` (CIMD-first registration, RFC 9207 `iss` validation, refresh-token request, per-issuer credential binding). The browser leg is a one-shot localhost redirect listener with best-effort auto-open (URL always printed); tokens persist to `~/.hakase/mcp-tokens.json` (0600, flocked, issuer recorded per SEP-2352) so restarts skip re-auth, and a per-server handler cache is invalidated when the config's OAuth block changes. The web read API redacts `client_secret`. **`hakase mcp serve`**: a new stdio MCP server exposes hakase's discovered markdown skills to any MCP host per SEP-2640 - `skill://index.json` enumerates them, each skill's `SKILL.md` and supporting files are readable as `skill://` resources byte-identically (discovery first-wins collisions preserved; read-only). Static `headers` auth keeps working and wins over OAuth bearer on conflict. See [docs/mcp-2026-07-28/](docs/mcp-2026-07-28/).

- **SkillOpt-Sleep (self-evolving markdown skills)** - markdown `SKILL.md` documents are now trainable: a Go-native port of Microsoft SkillOpt's SkillOpt-Sleep deployment workflow ([plan](docs/skillopt-sleep/plan.md); design port only, no code imported, attribution in the darwinian-evolver skill) that harvests session transcripts into redacted digests, mines recurring tasks with a deterministic train/val/test split (seed 42, dream-origin tasks quarantined to train), replays them against the skill document offline, reflects failures into bounded learned-block edits behind a strict held-out validation gate, and stages timestamped proposals pinned to the live file's sha256+realpath for explicit `hakase sleep adopt` - nothing touches a live skill without a human (or managed-only `--auto-adopt`). The `hakase sleep` CLI covers `harvest`/`review`/`run`/`dry-run`/`adopt`/`status`/`schedule`/`evalkit`; native cron `sleep` jobs are CLI-only (`sleep schedule`, the cronjob tool refuses privileged natives) and write `outputs/cron/sleep-*.md` reports. Safety posture (audit r2/r3 normative): harvest-time secret redaction before truncation with the opt-out flag-only (`redact_secrets:false` refused from config and env; `HAKASE_SLEEP_*REDACT*` hard-errors), machine-generated task files refused by real-backend runs until a human signs the `tasks.review.json` sidecar (`sleep review`), 0600/0700 writers with atomic installs and versioned `.bak` rollback (pruned to 3), spend guards (per-night deadline, per-task timeout, estimated token ledger, agentic tool-call budget), `.hakase/sleep-state.json` with flock + monotonic harvest checkpoint + hard model-change pause, and a deny-by-default replay audit (off-allowlist tool attempts + sandbox path refusals recorded in the night diagnostics). Optimizer maturity ships default-off: lr scheduling (constant/linear/cosine edit-budget decay) with rank-and-select when the optimizer over-proposes, slow-update trend guidance + a `references/optimizer-memory.md` sidecar prepended to reflect prompts (never deployed with the skill), skill-aware reflection (`execution_lapse` reminders land ungated in the protected appendix), BM25 lessons recall and quarantined dream rollouts, and a separate judge model (H2) that `sleep run` refuses to share without `--allow-shared-judge`. Claims discipline: accepted wins inside the noise band (< 1.5 points or val n < 20) are annotated `[noise-range]`, and `hakase sleep evalkit` produces the paired A/B (McNemar exact + bootstrap CI) any real claim must carry.

- **Visual Execution Canvas (ADK node graph)** - the web UI can now watch agent reasoning instead of a black box: a toggleable split panel in the chat view renders a live node graph (root orchestrator → delegation sub-agents → tool calls) driven by a new structured `graph` SSE event. The backend gained a typed `interfaces.GraphEvent` contract (`agent_start`/`agent_end`/`tool_start`/`tool_end`/`agent_text`/`agent_thought`/`transfer` with call ids, arguments, truncated results, durations, and error detail) emitted from two places: the shared `agentrun` driver loop (which now also surfaces ADK `transfer_to_agent` switches and attributes tool calls to the active agent node) and the delegation reporter (whose events finally reach the browser - they previously published to a global topic no web client subscribed to). Tool-call pairing is keyed by call id, synthesized for providers that omit them, which also fixes wrong durations when a sub-agent calls the same tool repeatedly. Payloads are capped at the source (args 8KB, results 64KB, text deltas 4KB). The SSE bridge retains the most recent 500 canvas events per session (in-memory ring, pruned on session delete) and a new `GET /api/sessions/{id}/graph` backfill endpoint rebuilds the canvas after a reload or mid-run reconnect; server restarts clear it. The `agentrun.EventSink` interface gained `OnGraphEvent`: the web bridge publishes under the session topic, Telegram mirrors it so phone-started runs render on the web canvas, and the TUI (which has its own delegation view) drops them. The canvas (Vue Flow, lazy-loaded into its own chunk) shows agent/tool nodes with live status and durations, groups delegation children under their open `delegate_task` call, and a click-through inspector with tabs for goal/arguments/tool output (copyable), the sub-agent's streamed thinking and output rendered as markdown, and the raw event JSON.

## [0.1.0-alpha.5] - 2026-09-07

### Added

- **Structured git tools** - `git_status`, `git_diff`, `git_log`, `git_branch` (read-only, no approval) and `git_stage`, `git_commit` (mutating) for the orchestrator and general-purpose agent. Every tool runs `git` through the same harmful-command policy, interactive approval gate, path audit, env scrubbing, and audit log as `system_exec` (`status`/`diff`/`log`/`branch` classify LOW/allow; `add`/`commit` MEDIUM/ask). Repo directories are sandbox-confined (write containment for mutations), output is bounded (256 KiB combined, 20k diff lines) and wrapped as untrusted data, and `GIT_TERMINAL_PROMPT=0` prevents hanging on credential prompts. Push/pull/clone/checkout/reset/clean are deferred to v2 - see [docs/git-tools/](docs/git-tools/).
- **Project-aware sessions** - the session is anchored to a project identity (the git root under the launch cwd, resolved by the new `internal/project` package; skill/AGENTS.md discovery already walked to the same root). The orchestrator and general-purpose agents receive a compact `GIT WORKSPACE` snapshot in their instructions at session start - branch and upstream tracking, staged/modified/untracked/conflicts counts, and the three newest commits - marked as a snapshot to re-check with `git_status`/`git_diff`. Git tools default `repo_dir` to the project root (after any explicitly pinned sandbox workspace), and the snapshot's token cost folds into the context-compaction reserve. Workspace (confinement) and project (identity) stay separate concepts; a registry + clone/push model for remote web deployments is deferred to v2 - see [docs/git-tools/project.md](docs/git-tools/project.md).
- **Remote git operations** - `git_clone`, `git_push`, and `git_pull` (the v2.1 remote slice) join the structured git toolset for the orchestrator and general-purpose agent. Clone sources are scheme-allowlisted (https/http/git/ssh; `file://` or local paths only when no sandbox is active, since they bypass the sandbox read roots) and targets resolve through write containment. Push exposes `--set-upstream` but never force-flags (that stays a HIGH-risk system_exec concern); pull is always `--ff-only` so an agent can never silently create merge commits. All three are MEDIUM-risk approval-gated network operations that run through the same policy/audit pipeline as every other git tool - see [docs/git-tools/](docs/git-tools/).
- **Destructive git operations** - `git_checkout`, `git_reset`, and `git_clean` (the v2.2 slice) complete the structured git toolset (12 tools total). Checkout switches branches (`-b` create) or restores one path from the index and never passes force flags - git itself refuses switches that would clobber uncommitted changes. Reset exposes soft/mixed/hard with revision-validated refs; `--hard` flows through verbatim so the existing gate classifies it HIGH and the approval card shows the real command. Clean always removes only untracked data (`-f`, or `-n` dry-run), with `-d`/`-x` mapped onto the existing HIGH combinations and an optional path filter. All three are approval-gated through the same policy/audit pipeline - see [docs/git-tools/](docs/git-tools/).
- **Project registry + materialization CLI** - `internal/registry` stores registered remote projects in `projects.json` under the hakase home (CRUD with id/name uniqueness and a source allowlist that mirrors git_clone: https/http/git/ssh, plus `file://` for local bare remotes). `internal/project` project identity became context-scoped (`WithRoot`/`RootFrom`, process-root fallback) so a server hosting several checkouts can resolve each run against its own project (DP-7). On top of it, `registry.Service` + `hakase projects list|register|sync|delete` materialize projects into `<hakase home>/projects/<id>` through the git_clone/git_pull engine under operator authority (DP-11, no second exec surface): register clones (cloning → ready, `sync_error` on failure with a retryable entry), sync fast-forwards (`--ff-only`; a diverged or dirty tree fails into `sync_error` without ever deleting local work), delete removes the checkout and entry and never touches the remote. Checkout paths derive from the store location, so a temp-home registry keeps its checkouts in its own tree. Local TUI/local-web behavior is unchanged - the registry is additive, targeting remote-web deployments - see [docs/git-tools/project-registry.md](docs/git-tools/project-registry.md).
- **Project registry web API + session binding** - remote-web deployments can now drive the registry from the UI: `GET/POST /api/projects`, `POST /api/projects/{id}/sync` and `DELETE /api/projects/{id}` under the existing auth middleware (register clones synchronously; a failed register/sync is returned as a `sync_error` entry with the bounded git error so the UI can retry via sync). Sessions gained a `project_id`/`project_name` binding: `POST /sessions` accepts `project_id` and validates it against the registry (ready checkout only), and the session list/detail responses expose the binding. Project-bound chat runs anchor to the project checkout (DP-7): the run context carries the checkout as the project root so git tools - including delegated runs - default there, and a fresh per-session `GIT WORKSPACE` snapshot is injected at the start of each bound run. Unbound sessions keep the process sandbox as-is; project-bound sessions on sandboxed hosts derive a per-session sandbox pinned to their checkout (see the per-run sandbox pinning bullet below). See [docs/git-tools/project-registry.md](docs/git-tools/project-registry.md).
- **Project registry UI + remote-deployment docs** - the New Session dialog lists ready registered projects (from `/api/projects`) so a session can be bound to a project checkout at creation; bound sessions are tagged with a git-branch chip in the session list and the chat header, and choosing one jumps straight into the bound conversation. The README's Production Deployment section now covers registered projects for remote-web hosts: registration (`hakase projects` / the API), session binding, and the DP-8 credentials note (clone/push/pull use the host's own git auth - credential helpers, `gh`, SSH agents - nothing is stored in `projects.json`).
- **Per-run sandbox pinning for project-bound sessions** - closes the DP-7 confinement gap: when the host sandbox is active, a registered-project session's git, file, and exec operations are confined to the project checkout instead of the process-wide workspace. `internal/sandbox` gained context-scoped sandbox plumbing (`WithConfig`/`ConfigFrom` - a per-run override consulted before the boot `CurrentSandbox` - and `PinnedTo`, which copies the active sandbox with workspace/read roots replaced by the checkout; sandbox-off stays off). The ctx-aware resolver is used by file ops (`taskResolve`), the git engine (`resolveRepoDir`/`runGit` via the new `BuildExecCommandFor`), and the `system_exec` handlers; web chat applies it in `runAgentTask` for bound runs, and delegated sub-runs inherit it through the run context. Unbound/local sessions are unchanged.
- **Workspace-hygiene git tools** - `git_stash` and `git_tag` (the Phase 7 first slice) bring the structured toolset to 14 tools. `git_stash` lists/saves/restores uncommitted work (`push -m`/`-u`, `pop` of the newest entry or a named `stash@{n}`; pop conflicts stay in the tree and are reported, never silently dropped). `git_tag` lists, creates lightweight or annotated tags (`-a -m`) at a commit-ish (default HEAD), and deletes (`-d`); names are validated against git's check-ref-format rules. Mutating operations are approval-gated through the same policy/audit pipeline. `git_remote`/`rebase`/`merge`/`--amend` stay out pending product decisions, with a recorded prerequisite (D18) to tighten `remote`/`branch` gate classification before any structured remote/branch tool - see [docs/git-tools/](docs/git-tools/).
- **Projects page (web UI project management)** - a `/projects` management page now sits beside Sessions. Each registered project renders as a row with its status (ready / cloning / sync error - the bounded git error of a failed clone or pull is shown inside the row, which is the retry surface), clone URL and pinned ref, checkout path and freshness, plus per-row **Sync now** (client-guarded against double-clicks; the server pull stays `--ff-only`), **New chat on this project** (starts a fresh bound session and jumps into it - conversations are never re-pointed at another repo), and a confirm-gated **Delete** whose wording states the remote repository is never touched. The **Register Project** dialog (name + clone URL + optional ref) validates through the existing endpoints, keeps the dialog open on a rejected name/URL, and lands a failed clone as a `sync_error` row. UI-first over the P3 endpoints - no new server surface. See [docs/git-tools/project-ui.md](docs/git-tools/project-ui.md).
- **Project status + sync safety guards** - ships the remaining `project-ui.md` items. New `GET /api/projects/{id}/status` reports a ready checkout's branch/upstream, ahead/behind (after a bounded best-effort fetch; `?fetch=0` for a local-only read), and staged/modified/untracked/conflicts counts, via the new sandbox `OperatorFetch`/`OperatorRepoState` (operator authority, no approval). The Projects page shows `N behind` / `N ahead` badges per ready project when it is opened and refreshes them after each sync. The sync endpoint now refuses with a 409 (never a `sync_error` transition) when an agent run is active on that project (`activeProjectRuns`, tracked per bound run), when the checkout holds uncommitted **tracked** changes (`ErrWorkingTreeDirty` - untracked files alone never block a pull), or when another sync is already running on the same project (`ErrBusy` per-project slot - the "page refresh mid-sync" double-run guard). Delete refuses under an active run or in-flight sync too. The chat header chip for a bound session now shows the checkout's live branch plus an amber dirty dot (per-category counts in the tooltip), read local-only when the conversation opens.
- **Telegram channel (transport-neutral channels subsystem)** - chat with hakase from your phone: a new `internal/channel` subsystem (deny-by-default pairing/auth, per-chat run state, bridge event router, outbound formatting; pairing state persists in `~/.hakase/channels.json`, 0600 + flock, sandbox-denied) with the Telegram bot as its first transport (`internal/channel/telegram`, `go-telegram/bot`). The bot runs **inside** the `web`/`serve` process and reuses its runner, approval/clarify gates, and SSE bridge, so approvals and clarifications can be answered from the phone or the web UI - first responder wins, and channel runs stream into the web UI too. One Telegram topic = one session: every thread in the DM is its own conversation (the topic auto-renames to the session title, parallel topics run concurrently, replies always land in the thread you typed in, `/topic <session-id-prefix>` binds an existing session, `/new` resets, the root area becomes a lobby), with optional `"pins": true` pinning your prompt for the duration of each run. Agent runs stream into one progressively edited message (created the moment the answer starts) with a quiet status line alongside, a 👀/👍/👎 reaction receipt on your prompt, approvals arriving as ✅/❌ buttons and clarifications as choice buttons. In-chat commands: `/new`, `/sessions`, `/use <id>`, `/topic`, `/status`, `/stop`, `/tasks`, `/cron [run|pause|resume <name>]`, `/notify on|off`, `/id`, `/help`; photo captions are supported (albums buffer into one prompt). Access is deny-by-default: statically allowlist IDs via `allowed_user_ids`, or pair at runtime with a 15-minute one-time 6-digit code (server console, `hakase channels pair-code`, or the Channels page); unpaired users get a terse, rate-limited reply. Manage everything from the web UI's **Channels** page (status, pairing code, revoke) or `hakase channels status|pair-code|revoke`; env overrides `HAKASE_TELEGRAM_ENABLED`/`HAKASE_TELEGRAM_BOT_TOKEN`. Underneath, `internal/agentrun` is a transport-neutral single-turn driver extracted from the web chat handler, so Telegram runs get the same sandbox, project binding, tool-call repair, and persistence as browser runs (one run per chat; `/stop` cancels) - see the Channels (Telegram) README section and [docs/superpowers/specs/2026-09-06-telegram-threads-design.md](docs/superpowers/specs/2026-09-06-telegram-threads-design.md).
- **Built-in keyless web search fallback** - when no research-capable MCP server (browser/search MCP) is connected, the agent keeps web research via built-in `web_search` and `web_fetch` tools: keyless DuckDuckGo HTML search with a Wikipedia API supplement, and page fetching through Jina Reader with a direct-GET fallback, all SSRF-guarded via the vision package's public-host checks. A dynamic ADK `tool.Toolset` (`internal/agent/websearch_fallback.go`) probes the MCP manager's current tool names on every `Tools()` call (ADK re-evaluates per model turn) and yields the tools only when no name matches a research hint; wired into the orchestrator, `web_researcher`, and `BuildSubAgentTools`. On by default; `web_search.enabled = false` in config.json is a kill-switch, with a force flag to override detection - see [docs/superpowers/plans/2026-09-07-web-search-fallback.md](docs/superpowers/plans/2026-09-07-web-search-fallback.md) and [docs/browser-mcp-presets.md](docs/browser-mcp-presets.md).
- **MCP failure cooldown with backoff** - a failed connect/list now arms a per-server cooldown (30s doubling to 5m) during which `Tools()` skips the server without dialing or logging, so a dead browser MCP costs one attempt per window instead of one per model call - and the web search fallback's second probe per turn is free. Recovery is detected on the first probe after expiry; manual `/mcp` reconnect clears the cooldown. `timeout_ms` (previously reserved) is now honored on http servers (default 10s) so a hanging endpoint fast-fails into the same path.
- **Session rename + archived-session management (API and web UI)** - sessions gained a rename API (`POST /api/sessions/{id}/rename`), and archived sessions are now exposed and restorable (`GET /api/sessions/archived`, `POST /api/sessions/{id}/unarchive`); the web UI's Sessions page adds rename, delete, and restore actions, and the chat header supports inline renaming of the conversation title.

### Fixed

- **Project register/sync failed with "outside approved workspace" when the server ran inside a git repository** - a web server with no sandbox config defaults to a paths sandbox rooted at its working directory, so when hakase was launched from inside a repo its managed checkouts under the hakase home fell outside the approved workspace and every operator clone/pull was refused in ~1 ms. Operator-issued registry git work (DP-11) now runs with the effective sandbox off (`operatorExecCtx`), and clone-source validation (D9) consults the effective context sandbox instead of the process-global one - so agents under a sandbox are still kept to remote sources, while `hakase projects register` keeps accepting local bare remotes.
- **CodeRabbit review hardening (PR #6)** - fixed every confirmed review finding on the branch: `git_commit` `short_sha` is now sliced from the raw rev-parse output before untrusted-data wrapping (it previously captured framing markers); clone sources starting with `-` are rejected (they would be parsed as git options); `POST /sessions` validates the `project_id` binding *before* persisting a session (no orphan rows on unknown/unready projects); `Service.Register` holds the per-project busy slot across materialization so Sync/Delete cannot race a `cloning` entry; plain `http://` was dropped from the registry source allowlist (https/git/ssh/file only, with matching CLI/API/docs/UI text); the register dialog guards against double submit; the git capture path in `runGitOpt` is race-free (mutex-guarded `cappedCapture`, atomic timeout flag); `util.cmdctx` no longer reads `cmd.Process` before `Start` and terminates processes canceled during the Start window (regression-tested under `-race`); `effectiveChildDir` derives its root from the effective sandbox parameter, not `CurrentSandbox`; the git-workspace/context token estimates use mutex-guarded setters (SetupRunner may run concurrently across sessions); registry/git test helpers pin `GIT_CONFIG_GLOBAL=/dev/null` with explicit author/committer env so tests never depend on the developer's `~/.gitconfig`; `TestProjectAPIUnavailable` restores `registry.Current`; the PDF report skill canonicalizes absolute output paths through the same current-directory containment check (with a self-test); and the `project-registry.md` JSON example matches the persisted flat schema. The remaining CodeRabbit suggestion - threading the per-run git-snapshot token estimate through each session's compaction reserve instead of the process-wide boot estimate - is a larger compaction-budget redesign and is tracked separately.
- **`GET /api/config` returned Telegram/sidekick secrets verbatim** - the endpoint's blanked-secrets contract was broken for the new channels config: `channels.telegram.bot_token`, the static pairing code, and (pre-existing) `sidekick.api_key` were returned in the clear. Presence is now reported via `has_telegram_bot_token` / `has_telegram_pairing_code` / `has_sidekick_api_key` flags with the values blanked, guarded by a regression test asserting the raw secrets never appear in the response body.
- **Telegram transport robustness** - stale webhooks are deleted before polling starts (with diagnostics via a direct HTTP GET), 409 webhook conflicts are verified and healed mid-poll instead of silently failing, a send-limiter livelock in `waitTurn` is resolved, parallel runs are isolated per session, bot/service messages are ignored on inbound, and client-created threads are respected (bridge parity with the topics model).
- **Sandbox fail-loud (issue #14)** - closed the two silent-isolation-loss gaps: `sandbox.mode: landlock` is now refused at config load (and at exec time for directly-constructed configs) with an actionable error instead of silently degrading to path-auditing-only exec; bubblewrap fallback without `bwrap` on PATH still requires explicit `sandbox.allow_fallback` (default false, unchanged) but when it fires every degraded exec is audit-logged (`decision: sandbox_fallback`) and surfaced in the web UI / TUI for that run, plus a startup warning is emitted and `GET /api/ready` reports the sandbox unavailable (degraded readiness).

## [0.1.0-alpha.4] - 2026-08-31

### Added

- **Native Windows port (Path A)** - hakase now builds and runs natively on Windows (`GOOS=windows`, no WSL2 required). Shell routing uses `cmd /D /C`, executable lookup is PATH-only with `NoDefaultCurrentDirectoryInExePath=1` and workspace-hijack rejection, the Python interpreter probes `py -3` then `python` with `.venv\Scripts` layout, file locking uses `LockFileEx`, process trees are tracked via Job Objects (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`), and Win32 path aliases (trailing dots/spaces, ADS streams, `\\?\`/`\\.\` namespaces, drive-relative `C:foo`, 8.3 short names, `%VAR%`/`!VAR!` expansion including whitespace names) are rejected or canonicalized via `GetFinalPathNameByHandle`. Bubblewrap/landlock modes coerce to `paths` with a warning on Windows. A `windows-latest` CI job runs the full test suite and a web boot smoke test; `make build-windows` cross-compiles `hakase.exe` and assembles the unsigned `dist/hakase-<version>-windows-amd64.zip` (see Windows notes in the README).
- **Any-browser MCP presets** - `docs/browser-mcp-presets.md` ships four copy-pasteable MCP server presets for the `web_researcher` (Lightpanda, `chrome-devtools-mcp` on Edge, `@playwright/mcp`, `@browsermcp/mcp`) with `tools.include`/`tools.exclude` shaping and a runtime tradeoff matrix. The browsing stack is a config-only swap on Linux and Windows alike.
- **Web UI slash-command palette** - typing `/` in the web chat input opens an autocomplete popup (arrow keys navigate, Tab/Enter complete, Esc dismisses) exposing the TUI commands except `/exit`: `/compact [focus]` (new `POST /api/sessions/{id}/compact` endpoint running the same snip + async summary cascade), `/sidekick <question>`, `/new`, `/sessions`, `/board`, `/mcp`, `/help`. Unknown `/tokens` pass through as ordinary text.
- **Sidekick agent** - a second, independently-configured LLM that answers direct questions (`/sidekick <question>` in the TUI or typed in the web chat) or quietly watches a run and surfaces advisory notes as quiet inline chips. On-demand asks are framed with a bounded recent-conversation transcript (`transcript_window_chars`, tail-biased) so follow-up questions have context. Explicit interactions are persisted to the session file under `"kind": "sidekick"` (answers carry `"role": "sidekick"`) so provenance is auditable. Modes `off` / `on_demand` / `watch` / `full`; no notification dispatch; local `openai-compatible` models keep conversation excerpts on-machine. See the README Sidekick section.

### Fixed

- Windows sandbox audit now rejects `%VAR%` and `!VAR!` (including `!X Y!`) expansion tokens before `cmd.exe` expands them (CWE-22).
- Python `pip` spawns use bounded waits: on cancellation the whole process tree is killed before `Wait` so output pipes inherited by descendants cannot block forever.
- Tightened several Windows correctness and docs issues flagged in CodeRabbit reviews (Pdeathsig assertion, symlink test scoping, `USERPROFILE`/`HOME` alignment in skill discovery tests, zip fallback, shell-routing docs).
