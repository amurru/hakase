# Changelog

All notable changes to hakase are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
During the alpha phase (0.x), breaking changes may land in any minor release;
the web UI and `config.json` formats aim for backward compatibility but are not
guaranteed stable until 1.0.

## [0.1.0-alpha.8] - 2026-09-27

### Fixed

- **A single unreachable MCP server could stall every model call.** `Tools()` runs before every model call, and two faults compounded on that path. The failure cooldown was armed with a timestamp captured *before* the dial, so for any server slower to fail than the window being armed, the cooldown was written into the past and the backoff never engaged - dead servers were re-dialled on every turn. And `timeout_ms` bounded a single attempt while the go-sdk retries a failed initialize 5 times and then sleeps through a backoff that ignores context cancellation, so it bounded the wrong thing. A traced run of "what's the real price of crypto trading?" took **191 seconds, 155 of them (81%) spent dialling one unreachable server, twice in the same turn.** The cooldown is now armed from when the failure was observed and floored at the attempt's own duration, and the whole SDK call is raced against a 6s list budget and abandoned when it expires. Measured on the machine the regression came from: that server takes **82.6s to fail before, 6.0s after** - and once per session rather than once per model call. An explicit larger `timeout_ms` is still honoured rather than truncated.
- **Simple questions cost several model round trips before the first word of an answer.** The orchestrator's instruction required two knowledge lookups "at the start of a session, before planning", a `list_tasks` preamble for task-shaped work, and up to four lookups before a filesystem search for an artifact location. Every tool call is a full round trip, so a one-line question paid several turns of pure overhead - the model was complying, not misbehaving. Those lookups are now reactive: consult prior lessons when the task resembles something previously hard-won or you are repeating an approach that failed, recall a note when the question is about a topic you have notes on, open the task board for genuinely multi-step work. The capabilities and the useful guidance are unchanged, including checking the task board first for artifact paths - it just no longer fans out to four tools before answering.

### Added

- **`hakase mcp doctor`** - measures every configured MCP server's tool count and dial time, bypassing the cache and the failure cooldown so it reports the real cost. The dial time is the number that matters, and nothing previously distinguished "connected slowly" from "unreachable". Servers already served from the tool-list cache report as `ok (cached)`, which is the steady state for a healthy one. It also surfaces servers whose toolset failed to build, which `Tools()` otherwise skips silently.

### Changed

- **The system prompt is ~36% smaller, and no longer re-invalidates the prompt cache every minute.** Three separate costs, all paid on every single model call since the system prompt is the request prefix:
  - the time reminder rendered the wall clock to the second and was cached by the minute, so a long-running session lost its entire conversation cache once a minute. It now renders the calendar date and is cached by day. Nothing needs the exact time - `cronjob` takes relative forms the server resolves, and `system_exec` can read the clock.
  - the skill index was 58 KB of the 69 KB prompt, mostly waste: the "call `load_markdown_skill` ..." sentence repeated once per skill, and every entry advertised an absolute path the model never used. With the 148 skills this repo ships, the prompt drops from 69,024 to 44,278 bytes. Descriptions are unchanged and the per-entry `<UNTRUSTED_DATA>` marker is a security control, so neither was touched.
  - MCP tool lists are now cached for 60s instead of being re-fetched before every model call. ADK calls `Tools()` per turn and the web-search fallback probes it a second time, so a healthy server was paying a connect+list round trip twice per turn - a process spawn for stdio, a network round trip for HTTP. Failures are deliberately not cached, so a server that comes back is picked up on the next probe rather than staying failed for the TTL; the existing cooldown gate still paces retries, and a manual reconnect invalidates the cache.

## [Unreleased]

### Added

- **Hybrid knowledge retrieval (embeddings + BM25 via RRF)** - opt-in dense retrieval fused with the existing fielded BM25 through Reciprocal Rank Fusion: `hybrid_search: true` with `knowledge_embed_model` (e.g. `nomic-embed-text` on Ollama, `text-embedding-3-small` on OpenAI; `knowledge_embed_base_url` overrides the endpoint, defaulting to the primary `base_url`) routes `search_knowledge` through `HybridSearch`, which cosine-ranks every gate-passing note against the query embedding and fuses with BM25 — paraphrase queries recall notes with no token overlap while exact-identifier queries keep BM25 precision. Vectors persist as sidecars (`<knowledgedir>/vectors/<slug>.vec.json`, validity-gated on note mtime/size + model/dim, lazy batched backfill), so files stay the source of truth with zero new dependencies. Default off: byte-identical search, no network. Runtime endpoint failures degrade to BM25 with a log line (static misconfig fails fast at load); sleep recall and web REST stay BM25-only by design. CLI: `knowledge search --hybrid`, `knowledge bench --hybrid` (BM25 vs hybrid tables). See `docs/hybrid-retrieval/spec.md` HR-001..HR-008.

- **Piper TTS audio provider (`generate_audio` works)** - the existing local Piper TTS (previously Telegram voice replies only) is routed through the media registry as the `piper` audio provider: `audio_provider: piper` with a `text_to_speech` default voice resolves and synthesizes OGG/Opus into the media store (120s default timeout, semaphore, manifest line, `<audio controls>` snippet). `voice` selects the per-language voice like Telegram; default stays `off` with the verbatim actionable message. `openai`/`elevenlabs` remain accepted-but-unwired forward-compat. See `docs/media-generation/spec.md` MG-012.

- **Project-scope hooks with content-hash trust** - `<project-root>/.hakase/hooks.json` layers project `PreToolUse` / `PostToolUse` / `SessionStart` hooks under the user config (user layer runs first; project files can only add hooks, never disable user hooks or the trust gate). Project handlers execute only after explicit per-hook trust (`hakase hooks trust [--all] [--yes] [fingerprint-prefix]`): the trust key is a content hash over the resolved argv plus local script bytes, so rewriting a script body lapses trust and the hook is skipped loudly until re-trusted. Untrusted hooks never execute — not a warning that proceeds. This deliberately adopts Codex's content-hash model, not Gemini CLI's fingerprint-and-approve (known-broken, gemini-cli#27900).
- **`SessionStart` hooks** - run once per session with stdout/JSON context injected at the head of the first turn (alongside the auto-memory block); empty renders roll back so mid-session trust grants fire later. `hakase hooks test <name|prefix>` dry-runs any handler with a sample payload and prints the verdict.
- **Hook-config write protection** - `~/.hakase/hooks-trust.json` joins the sandbox sensitive-files deny list, and agent writes to any `*/.hakase/hooks.json` are denied in path confinement (reads stay allowed). Even if a write landed another way, the trust gate still refuses to execute untrusted hooks.
- **`UserPromptSubmit` hooks** - run on every user prompt with the prompt text in the payload, so hooks can react to content (e.g. inject repo context for test-failure questions); context prepends to the turn, fired once per prompt via a HistoryBuilder slot keyed on message sequence.
- **Hook management without restarts** - per-hook `"enabled": false` skips execution without touching the content fingerprint (toggling never lapses trust), and user-layer edits recompile the live runner in place: `hakase hooks add/rm/enable/disable/on/off`, `POST /api/hooks/user/*` + `/master` behind a full web Hooks page (list, trust, revoke, add/edit forms), and TUI `/hooks` subcommands (`trust --yes` with script-preview review, `test`, `add/update/rm/enable/disable/on/off`). External CLI edits reach a running server via SIGHUP; trust grants need neither (mtime-cached). See [docs/hooks/usage.md](docs/hooks/usage.md).

## [0.1.0-alpha.7] - 2026-09-27

### Changed

- **Releases are now published as prereleases** - every release up to and including `v0.1.0-alpha.6` was created without `--prerelease`, so GitHub treated a `0.x` alpha as the latest stable release: `/releases/latest` resolved to an alpha and upgrade tooling would follow it as though it were stable. New tags are flagged at creation, and `v0.1.0-alpha.6` was re-flagged. **Consequence:** `/releases/latest` now resolves to the newest *stable* release rather than the newest alpha, so anything following that redirect - a script, a `curl .../releases/latest/...` URL, a packaging helper - gets `v0.1.0-alpha.5` until a non-prerelease ever ships. Pin a tag or a version instead if you want the current alpha. Nothing in this repository relied on that redirect (the AUR `PKGBUILD` pins a tag URL), and the flag applies only at creation, so re-running a release for an existing tag will not re-flag it.
- **mermaid 11.16.1 -> 12.0.0, and diagrams now render differently** - a deliberate major upgrade, but it carries three changes worth knowing about before you file a bug. `useMermaid.ts` configures only `startOnLoad` and `securityLevel`, so all three of mermaid 12's new defaults apply: (1) **the default layout flips from dagre to ELK** for flowchart, state, class, ER, requirement and use-case diagrams, which upstream describes as changing how existing diagrams look; (2) **the default theme becomes `redux-color` and the default look `neo`** for ten diagram types including sequence and state, so those change appearance too; (3) **the browser floor rises to Safari 17.4+ / ES2024** and Node 22.12+ (mermaid is lazily imported, so this only affects a client that actually renders a diagram, not the rest of the web UI). ELK ships bundled now, so no extra install; its code is fetched only when a diagram uses it, and the tiny build still falls back to dagre. The previous appearance is one line away if it turns out to be unwanted: `layout: 'dagre'`, `theme: 'default'` and `look: 'classic'` in `mermaidOptions`. Unaffected by this upgrade: the Visual Execution Canvas, which is a Vue Flow graph rather than mermaid.

### Fixed

- **Concurrent web dictation was unbounded** - the per-request limits on `POST /api/transcribe` bound each request but never the *number* of them, so N simultaneous dictations ran N ffmpeg + `whisper-cli` pairs on one host. A user holding the mic, or a handful of tabs, could saturate the CPU that a single transcription is meant to get. Transcription is now serialized process-wide through the same `speech.Queue` the Telegram voice path uses, capped at 3 concurrent (one in flight, the rest queued); a request past the cap is refused immediately with 503 "Transcription queue is full - try again in a moment" instead of piling up work. The composer's existing error toast surfaces that with no UI change, and the model warm-up deliberately stays outside the queue so a multi-hundred-MiB download never holds the worker. **Behavior change:** a heavily contended host can now return 503 where it previously queued the work.
- **Telegram voice notes ran the first-use model download under the transcription timeout** - `speech_to_text.timeout_seconds` (180s) is sized for a short decode plus inference, but `Transcribe` also fetches the ggml model on first use, and that is a network transfer of tens to hundreds of MiB. On a slow connection a first voice note could never finish: the download was killed at 180s and every retry started over. The voice path now warms the model under `speech_to_text.model_timeout_seconds` (default 1800, added for the web dictation endpoint in alpha.6) before the transcription budget starts, so `Transcribe`'s internal lookup short-circuits on the file already being on disk. When the model is present this costs one `os.Stat` per message. Mirrors the web dictation handler, so the two transports now behave the same.
- **A failed model download leaked internal hosts into the Telegram chat** - the download error embeds the configured `speech_to_text.model_url_base` and on-disk model paths (e.g. `downloading whisper model "base-q5_1" from http://mirror.internal/...`), and it was being echoed into the chat. A chat is not a single-operator surface, so the detail now goes to the server log and the reply is a fixed line pointing there - the same property the web endpoint's 503 got in alpha.6. The pre-existing `Availability` hint is unchanged, since it names config keys the operator chose rather than environment internals.

## [0.1.0-alpha.6] - 2026-09-25

### Added

- **MCP server mode (`hakase mcp serve --agent`)** - hakase runs are now an MCP tool, so another agent (Claude Code, Codex, any MCP host) can drive hakase as a sub-agent: the new `internal/mcp/runserver` mounts a `run` tool (send a prompt, block until the turn ends, get the answer plus a bounded activity log, token usage and the session id), `list_sessions`/`get_session` (session discovery and message reads), and the `skill://` resources of the skills-only server on one stdio connection (server name `hakase`; the default `hakase mcp serve` stays skills-only and still boots no model wiring). `run` drives the same transport-neutral `agentrun.Driver` as the web chat and Telegram - identical sessions, persistence, project binding, sandbox pinning and tool-call repair (persisted user turn first, one run per session, 8 concurrent runs cap, per-call `timeout_seconds` default 900s) - so an MCP-driven run is visible in the web UI and resumable from the phone. Stream deltas and activity lines go out as MCP progress notifications, and mid-run **approvals/clarifications reach the driving client's human per SEP-2322**: the `run` call suspends with an `input_required` result carrying the elicitation (protocol 2026-07-28 forbids standalone server-initiated elicitation, and go-sdk v1.8 enforces it; pre-2026-07-28 clients are fulfilled transparently by the SDK), the client's answer resumes the suspended run via a random `RequestState`, and every failure path (no run bound, expiry, unfulfillable client, declined dialog) fails closed exactly like headless hakase - with `approval.mode` allow/deny short-circuits honored. The agent bootstrap (config → tracing → sandbox → sessions → registry → deps → gates → runner) lives in package main (`cmd/hakase/mcpserver.go`) behind a `cli.MCPAgentServeFn` injection hook - the web/serve/tui pattern - since the deps factories are main-only; `run` runs carry `transport: "mcp"` in traces. See [docs/mcp-server/](docs/mcp-server/spec.md), and [#45](https://github.com/amurru/hakase/issues/45).
- **Telegram voice notes in (local whisper.cpp), voice replies out (local Piper TTS)** - voice messages are no longer dropped: an inbound voice note downloads through the same getFile path as photos, decodes locally via ffmpeg to 16 kHz mono WAV, and transcribes through whisper.cpp (`whisper-cli`, model `base-q5_1` by default, auto-downloaded once from HuggingFace into `~/.hakase/models/whisper/` with an overridable URL base for offline setups). The transcript is echoed back (`🎙 Heard: …`) BEFORE the run starts so a mis-transcription can be stopped with `/stop`, then flows through the ordinary pairing/auth/agentrun path exactly like typed text; audio bytes never leave the machine and are never persisted (the transcript is the only trace). Transcriptions are serialized (one at a time, queue depth 3) with a "queue is full, try again" reply instead of piling up CPU work, `speech_to_text.max_seconds` (default 120) refuses marathon notes, and `timeout_seconds` (default 180) bounds each transcription. Missing tooling degrades gracefully with an actionable hint naming the config block and what to install - never a run failure, never silence. Config: `speech_to_text` (disabled by default; `HAKASE_TELEGRAM_STT_ENABLED`). **Voice replies** complete the loop: with `text_to_speech` enabled (Piper — `pip install piper-tts` — plus a `.onnx` voice and ffmpeg), `/voice auto` speaks the answer back when you spoke to it, `/voice on` speaks always, `/voice off` (default) stays text; the preference persists per chat, voice turns suppress the text stream (status line only) and speak the full markdown-stripped, length-capped answer as one OGG/Opus voice note, and any synthesis failure falls back to the normal text answer. Voice models live in a single `voices` map — the reserved `"default"` entry plus one per language — and the reply **mirrors the language whisper detected** on the inbound voice note (German in, German speech out), falling back to the default for unconfigured languages and typed prompts. The transport-neutral `internal/speech` package hosts both pipelines - see [docs/telegram-voice/](docs/telegram-voice/spec.md).
- **Web UI voice dictation (local whisper.cpp)** - the web composer can now be talked to: a mic button beside the attach button records locally through `MediaRecorder` (`audio/webm;codecs=opus` where supported, with plain WebM, OGG/Opus and MP4 fallbacks), shows a live elapsed-time chip with cancel, and on stop uploads the clip to a new auth-gated `POST /api/transcribe` (`multipart/form-data`). The handler runs the same `internal/speech` whisper.cpp pipeline as Telegram voice notes, reading the same `speech_to_text` block for model, binary paths, model dir and limits - but not gating on `enabled`, so dictation works as soon as the tooling is present. The transcript lands in the composer as **editable text before anything is sent**, so a mis-transcription is caught before it becomes a prompt. The audio is transcribed by your own hakase host and never handed to a third-party STT service; it is not persisted either, so the only durable trace is the resulting text. (On a remote deployment the recording does cross the wire from the browser to your server - the local guarantee is about the transcription, not the transport.) Every failure path degrades to a toast rather than a lost prompt: denied microphone permission, a missing `whisper-cli`/ffmpeg (503 carrying the actionable install hint that names the config block), and a silent recording ("no speech detected") are each reported in place, and the recorder stops its own media tracks on stop and cancel so the browser's mic indicator goes dark. The endpoint is bounded on both axes: a hard 25 MiB request cap (413 past it) and `speech_to_text.max_seconds` enforced against the decoded audio rather than a client-supplied duration, so a caller that cannot state a duration no longer gets an unbounded transcription. Closes the "Web UI voice input" item that alpha.5 listed as planned.
- **Session checkpoints / restore-to-message rewind** - every conversation now has rewind points: a snapshot of the full session file is taken just before each user message is recorded (web chat, TUI send paths, and Telegram all flow through the one persistence choke point), stored under `sessions/.snapshots/<session id>/` (0600, atomic writes under the store's flock, invisible to the session index) with a per-session retention ring (`session.snapshots.max`, default 50; `session.snapshots.enabled: false` stops taking them). "Restore to before this message" on any persisted user prompt in the chat UI opens a snapshot dialog (timestamp, message count, preview, preselected to the prompt's own rewind point) and restores in three clicks: the current state is first captured as a `pre-restore` undo snapshot — so restore is itself undoable — then the session file is replaced with the snapshot's content through the store's atomic path, keeping the same session id so project binding and registered-project sandbox pinning survive (acceptance criterion 3). Restore refuses with 409 while the agent is working (same guard as compact), snapshots die with their session (delete + stale cleanup), and everything is truncation-with-a-net rather than branch-fork — see [docs/session-rewind/](docs/session-rewind/spec.md).
- **OpenTelemetry GenAI tracing** - one waterfall trace per agent run, exported over OTLP/HTTP to any GenAI-aware collector (Jaeger, Grafana Tempo, Langfuse, Datadog): a `hakase.run` correlation root per transport run (session id, task id, bound project, transport, provider outcome mapped from the canvas status vocabulary) nests ADK's built-in GenAI spans — `invoke_agent` per agent activation, `generate_content` per LLM call with `gen_ai.usage` token counts (input, output incl. reasoning, cache reads) and finish reason, `execute_tool` per tool call — plus `retrieval knowledge` spans on `recall_knowledge`/`search_knowledge` with result counts. Web, Telegram, TUI, and cron runs all share one trace shape (the driver gained `agentrun.NewForTransport`; delegated sub-agent spans parent via ctx propagation with no delegation-code changes), MCP tool calls propagate W3C `traceparent` through `_meta` per SEP-414 via a go-sdk sending middleware, and the audit log's session id now joins to a trace via `hakase.session.id`. Off by default and honest about it: `tracing.enabled: false` installs nothing (no provider, no exporter goroutine, no network traffic), enabled tracing validates its endpoint at startup (fail-loud — the exporter itself only logs parse errors), a pathless endpoint targets the collector at `/v1/traces` while path-shaped vendor endpoints pass through verbatim, and `headers`/`sample_ratio` (default 1) cover vendor auth and head-based sampling. Env overrides: `HAKASE_TRACING_ENABLED` / `_ENDPOINT` / `_SAMPLE_RATIO` / `_HEADERS`. GenAI semconv are still Development status, so every hakase-owned attribute key is pinned as a literal in `internal/tracing` rather than tied to a semconv package version - see [docs/otel-tracing/](docs/otel-tracing/spec.md).
- **Agent-written auto-memory** - the orchestrator can now carry facts across sessions through its own notes: `remember` saves a short typed note (`user` / `feedback` / `project` / `lesson` — update by passing an existing id), `forget_memory` deletes one, and every new session starts with an `AUTO MEMORY` block (note ids included) injected once per session ahead of history, scoped to the session's project root plus global notes and capped by `memory.max_prompt_chars` (default 4000, truncation disclosed in-block). Notes persist at `~/.hakase/memory/notes.json` (0600, flock held across the read-modify-write transaction, atomic tmp+rename with mode tightening, corrupt-file quarantine, mirrors the channels-state store), are deduped on exact match, and the store refuses writes past `memory.max_notes` (default 200) with an actionable error instead of evicting silently. `memory.enabled: false` (or `HAKASE_MEMORY_ENABLED`) removes both the tools and the injection entirely; tools are orchestrator-only (sub-agents never see them). Surfacing for human pruning: a web UI Memory panel (list, filter, delete under the existing auth middleware) and `hakase memory list|add|forget`, which work while the server runs. The optional session-end extraction pass and a TUI command are deferred - see [docs/auto-memory/](docs/auto-memory/spec.md).
- **MCP 2026-07-28 upgrade (go-sdk v1.7 + ADK v2.4)** - the MCP client now speaks the stateless protocol revision: dependency bump (go-sdk v1.4.1 → v1.7.0, ADK v2.1.0 → v2.4.0, MVS-cascaded genai/openai-go/OTel) with old-revision servers still working via the SDK's negotiation fallback (covered by a stateful+stateless smoke matrix test). **Elicitation rides the existing gates**: every managed server gets its own MCP client with an elicitation handler that routes server input requests into hakase's approval/clarify machinery - a remote server's boolean confirm lands as an approval card (web UI + Telegram inline keyboards + TUI, first responder wins, session-routed), form fields as clarify prompts (JSON-schema enums become choice buttons, other primitives free text with type coercion), URL-mode elicitations surface the link as a non-blocking clarify prompt, multi-property schemas decline closed, and headless runs (cron) fail closed. Timeout maps to decline, user cancel to cancel. **OAuth for remote servers (CIMD)**: the reserved phase-3 `oauth` config stub became a real schema - `client_id_url` (Client ID Metadata Document, https + non-root path enforced) or pre-registered `client_id`/`client_secret`, optional `redirect_url`/`scopes` - wired through the go-sdk's `AuthorizationCodeHandler` (CIMD-first registration, RFC 9207 `iss` validation, refresh-token request, per-issuer credential binding). The browser leg is a one-shot localhost redirect listener with best-effort auto-open (URL always printed); tokens persist to `~/.hakase/mcp-tokens.json` (0600, flocked, issuer recorded per SEP-2352) so restarts skip re-auth, and a per-server handler cache is invalidated when the config's OAuth block changes. The web read API redacts `client_secret`. **`hakase mcp serve`**: a new stdio MCP server exposes hakase's discovered markdown skills to any MCP host per SEP-2640 - `skill://index.json` enumerates them, each skill's `SKILL.md` and supporting files are readable as `skill://` resources byte-identically (discovery first-wins collisions preserved; read-only). Static `headers` auth keeps working and wins over OAuth bearer on conflict. See [docs/mcp-2026-07-28/](docs/mcp-2026-07-28/).

- **SkillOpt-Sleep (self-evolving markdown skills)** - markdown `SKILL.md` documents are now trainable: a Go-native port of Microsoft SkillOpt's SkillOpt-Sleep deployment workflow ([plan](docs/skillopt-sleep/plan.md); design port only, no code imported, attribution in the darwinian-evolver skill) that harvests session transcripts into redacted digests, mines recurring tasks with a deterministic train/val/test split (seed 42, dream-origin tasks quarantined to train), replays them against the skill document offline, reflects failures into bounded learned-block edits behind a strict held-out validation gate, and stages timestamped proposals pinned to the live file's sha256+realpath for explicit `hakase sleep adopt` - nothing touches a live skill without a human (or managed-only `--auto-adopt`). The `hakase sleep` CLI covers `harvest`/`review`/`run`/`dry-run`/`adopt`/`status`/`schedule`/`evalkit`; native cron `sleep` jobs are CLI-only (`sleep schedule`, the cronjob tool refuses privileged natives) and write `outputs/cron/sleep-*.md` reports. Safety posture (audit r2/r3 normative): harvest-time secret redaction before truncation with the opt-out flag-only (`redact_secrets:false` refused from config and env; `HAKASE_SLEEP_*REDACT*` hard-errors), machine-generated task files refused by real-backend runs until a human signs the `tasks.review.json` sidecar (`sleep review`), 0600/0700 writers with atomic installs and versioned `.bak` rollback (pruned to 3), spend guards (per-night deadline, per-task timeout, estimated token ledger, agentic tool-call budget), `.hakase/sleep-state.json` with flock + monotonic harvest checkpoint + hard model-change pause, and a deny-by-default replay audit (off-allowlist tool attempts + sandbox path refusals recorded in the night diagnostics). Optimizer maturity ships default-off: lr scheduling (constant/linear/cosine edit-budget decay) with rank-and-select when the optimizer over-proposes, slow-update trend guidance + a `references/optimizer-memory.md` sidecar prepended to reflect prompts (never deployed with the skill), skill-aware reflection (`execution_lapse` reminders land ungated in the protected appendix), BM25 lessons recall and quarantined dream rollouts, and a separate judge model (H2) that `sleep run` refuses to share without `--allow-shared-judge`. Claims discipline: accepted wins inside the noise band (< 1.5 points or val n < 20) are annotated `[noise-range]`, and `hakase sleep evalkit` produces the paired A/B (McNemar exact + bootstrap CI) any real claim must carry.

- **Visual Execution Canvas (ADK node graph)** - the web UI can now watch agent reasoning instead of a black box: a toggleable split panel in the chat view renders a live node graph (root orchestrator → delegation sub-agents → tool calls) driven by a new structured `graph` SSE event. The backend gained a typed `interfaces.GraphEvent` contract (`agent_start`/`agent_end`/`tool_start`/`tool_end`/`agent_text`/`agent_thought`/`transfer` with call ids, arguments, truncated results, durations, and error detail) emitted from two places: the shared `agentrun` driver loop (which now also surfaces ADK `transfer_to_agent` switches and attributes tool calls to the active agent node) and the delegation reporter (whose events finally reach the browser - they previously published to a global topic no web client subscribed to). Tool-call pairing is keyed by call id, synthesized for providers that omit them, which also fixes wrong durations when a sub-agent calls the same tool repeatedly. Payloads are capped at the source (args 8KB, results 64KB, text deltas 4KB). The SSE bridge retains the most recent 500 canvas events per session (in-memory ring, pruned on session delete) and a new `GET /api/sessions/{id}/graph` backfill endpoint rebuilds the canvas after a reload or mid-run reconnect; server restarts clear it. The `agentrun.EventSink` interface gained `OnGraphEvent`: the web bridge publishes under the session topic, Telegram mirrors it so phone-started runs render on the web canvas, and the TUI (which has its own delegation view) drops them. The canvas (Vue Flow, lazy-loaded into its own chunk) shows agent/tool nodes with live status and durations, groups delegation children under their open `delegate_task` call, and a click-through inspector with tabs for goal/arguments/tool output (copyable), the sub-agent's streamed thinking and output rendered as markdown, and the raw event JSON.

### Changed

- **BREAKING: STT/TTS config moved to the top level** - `channels.telegram.speech_to_text` and `channels.telegram.text_to_speech` are now the top-level `speech_to_text` and `text_to_speech` blocks. They stopped being Telegram-specific once the web UI dictation endpoint started feeding the same transport-neutral `internal/speech` pipelines. The schema of each block is unchanged, so migration is a move rather than a rewrite: hoist the two blocks out of `channels.telegram` in `config.json` (`config.json.example` carries the new shape). There is deliberately **no** compatibility shim for the file - the loader ignores unknown keys rather than erroring, so an unmigrated `config.json` still loads but the speech blocks are silently ignored and both features stay off. Worth a look before you upgrade. The environment variables are the exception: `HAKASE_TELEGRAM_STT_ENABLED`/`HAKASE_TELEGRAM_TTS_ENABLED` still work as legacy fallbacks behind the new `HAKASE_STT_ENABLED`/`HAKASE_TTS_ENABLED`. Source compatibility was kept as well: `TelegramSTTConfig`/`TelegramTTSConfig` are now aliases of `STTConfig`/`TTSConfig`, and the `DefaultTelegram*` constants alias the renamed `DefaultSTT*`/`DefaultTTS*` ones. Validation error messages were re-worded to name the new paths.

### Fixed

- **Web dictation was not bounded by `speech_to_text.timeout_seconds`** - the `POST /api/transcribe` handler passed its bare `r.Context()` to the transcriber, and that context cancels only when the browser goes away, so a stalled ffmpeg or `whisper-cli` kept the request and its child process alive for as long as the socket stayed open (the 25 MiB body cap and the `max_seconds` length bound do not help - the cost is CPU in the child, not bytes, and the server sets no write timeout because of SSE). Unlike the Telegram voice path, the handler never applied the configured bound, even though it already loaded the value into the config it passed along. Transcriptions now run under `speech_to_text.timeout_seconds` (default 180, applied by `speech.STTConfig.resolved()` inside `NewWhisperCLI` even when no `config.json` exists, so this holds on a bare install too). The **first-use model download is deliberately not on that clock**: it is a network transfer of tens to hundreds of MiB, so bounding it at 180s would leave a slow connection permanently unable to complete a first run, and the ggml fetch was previously the one genuinely unbounded step (no client timeout, no `ResponseHeaderTimeout`). It now gets its own `speech_to_text.model_timeout_seconds` (default 1800), fetched before the transcription budget starts so `Transcribe`'s internal call short-circuits on the model already being on disk. A failed download returns 503 with a fixed "speech model unavailable - see server logs" body: `ensureModel`'s errors embed the configured `model_url_base` and on-disk model paths, so the detail goes to the server log rather than to any authenticated client (the `Availability()` hint next to it is left alone - it names config keys the operator chose, not environment internals).
- **MCP `run` progress notifications outlived their request** - a run that hits a gate spans several `run` calls (each round trip returns an `input_required` result and the client re-enters with a fresh progress token), but the run sink captured the token of the call that *started* the run. The run goroutine kept executing on its detached context after that call completed and kept emitting progress against the finished request, which a strict client may reject or drop. The sink is now bound and unbound around each handler invocation, so a delta that lands while no call is in flight is still accumulated into the result but never emitted, and a resumed call notifies under its own token.
- **Phantom scrollbar over the chat composer** - the transcript list rendered its wrapper even with zero messages, leaving 32px of dead scroll that pinned a scrollbar over the input, and the auto-growing textarea toggled `overflow` unconditionally, so fractional zoom/DPI rounding could show a scrollbar on an empty composer. The wrapper is now rendered only when messages exist, and the textarea only starts scrolling once the content genuinely exceeds the 8-line cap. The attach/mic/textarea/send row also became one bordered pill with the focus ring on the container (the textarea stays borderless), and the Vite dev proxy now honors `HAKASE_API`.
- **Voice dictation could leave the microphone stuck on, or upload a cancelled clip** - two bugs in the web recorder. Clicking the mic button twice while the permission prompt was still open started two acquisitions, and the second overwrote the first, orphaning its stream with no reachable Stop control (the browser's mic indicator stayed on); a pending-acquisition guard now claims the slot before the first `await`, and any stream acquired before a failure is released. And `MediaRecorder.stop()` delivers a final `dataavailable` event *after* `cancelRecording()` cleared the chunks, so Cancel could still upload the recording - and unmounting mid-recording hit the same path. A cancel flag set before stopping now short-circuits the upload.
